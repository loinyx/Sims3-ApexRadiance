## What was built

`0x006A8BA0` (thiscall(stopwatch*, float budget), ret 8) is 30 instructions with four calls [verified, disassembly
of the Steam 1.67.2 `TS3W.exe` copy]:

| Order | Site | Callee | Condition | New counter | Hook |
|---|---|---|---|---|---|
| 1 | CALL `0x006A8BAD` | `0x006A7CF0` rebuild, thiscall(level), no args, plain `ret` | `[level+0x280] == 0` | Room solve: rebuild | call site |
| 2 | `call edx` `0x006A8BD7` | driver `0x00688920` via slot `0x00FF05A0` (vtable `0x00FF0594`, `level+0x290`, wall AO) | `[level+0x88] >= 0` | Room solve: AO solver 1 | vtable slot |
| 3 | `call edx` `0x006A8BF1` | driver `0x00688920` via slot `0x00FF0720` (vtable `0x00FF0714`, `level+0x2E8`, step `0x0068A400`) | `[level+0x88] >= 0` | Room solve: AO solver 2 | vtable slot |
| 4 | CALL `0x006A8C0E` | `0x006A88B0` room pass, thiscall(stopwatch*, float), ret 8 | `[level+0x23C] != 0` | Room solve: room pass | call site |

- The x87 stack is empty at all four calls; none returns a value in ST0 [verified].
- Before the room pass the solve calls `0x006A4800`, a sun-direction change check (one getter, a few SSE ops) [verified];
  it stays in the remainder of "Lot room solve" with the branches. Remainder = Lot room solve minus the four lines.
- The two `call edx` sites are 2 bytes, so the solvers are timed by swapping their own vtable slots. The driver sits
  in a third slot, `0x00FF0580` of the base vtable `0x00FF0574`, which is left alone [verified: exactly three aligned
  dwords equal `0x00688920`].
- The four counters count only while a timed *Lot room solve* call is open on the same thread (`t_inRoomSolve`), so
  they split that line exactly. The synchronous level solve `0x006A4180` also drives both solvers (60,000 ms budget,
  lot LOD switch) [verified in room-light-maps.md]; it is left out.
- The wall shading gate (`lot_lighting_motion.cpp`) recognises the step's caller by a return address inside the driver;
  the new hook sits on slot +0xC, outside the driver, so the gate still sees the real driver [verified by reading the
  gate].
- AO solver 1 includes the existing *Wall AO pass* line (slot +0x1C, inside the driver).
- Signatures: `RoomRebuildCall` and `RoomPassCall` match once on Steam 1.67.2 [verified]. The EA `TS3.exe` copy at hand
  did not match the room solve's own existing signature either (the copy is not a plain image); other
  editions are open, and the counters are simply not installed there.

## S0-G1 job spec (`realtime-gi-profile`, for S0-13 to add)

S0-13 owns the job files; this is the content for the profile arm. One start, Developer build of `gi/s0-11` (or
later), Apex + bridge as for every game run. The pan matches run D of research 00 (150 m, 4 passes of 60 s).

```json
{
  "id": "realtime-gi-profile",
  "description": "Frame Profiler over the far pan of research 00 run D (8 lots at 150 m, 4 passes of 60 s) at night, with the four parts of the lot room solve timed (rebuild, AO solver 1, AO solver 2, room pass). Developer build; developer mode on, the background frame limit lifted. Read the counter block of ApexRadiance_Hitches.txt: the four Room solve lines against Lot room solve.",
  "save": "ApexTest-Night",
  "toml": {
    "ui": { "developer_mode": true },
    "screen": { "background_fps_limit": 0 },
    "qol.frame_profiler": { "start_at_load": true, "report_every_s": 60, "write_file": true }
  },
  "variants": { "profile": {} },
  "expect": ["\\[FrameProfiler\\] Measurement preset: timing run"],
  "fail": ["\\[FrameProfiler\\] Room solve: "],
  "steps": [
    { "do": "speed", "speed": "normal" },
    { "do": "wait", "minutes": 0.5 },
    { "do": "profile", "minutes": 4.5 },
    { "do": "camera_pan", "lots": 8, "height": 150, "seconds": 60, "passes": 4 },
    { "do": "wait", "minutes": 0.5 }
  ]
}
```

- `fail`: the profiler logs `[FrameProfiler] <target name>: <status>` only when a target does not attach, so any line
  starting with `Room solve: ` means a missing counter.
- Smoke (before the measured run): the same job with `"passes": 1`. Pass = no crash, no `fail` line, and the
  "Timed functions" block of `ApexRadiance_Hitches.txt` shows the four `Room solve:` targets as `Timed`, with
  non-zero calls in a 60 s report.
- Result to record in handoff.md: per 60 s report, render-thread ms and calls of Lot room solve and the four parts; the
  room pass share of the 2.81 ms a frame; then S1's claim is restated (design §3.7 gate).
