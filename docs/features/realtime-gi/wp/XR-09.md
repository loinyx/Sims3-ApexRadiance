# XR-09: what the per-pixel shadow kernel costs

Status: **done** (offline harness). Branch `gi/xr-09` (off `gi/xr-04`).

Marks: [V] verified by the harness on an RTX 3070 Laptop GPU, [I] inferred, [O] open.

## Answer

The kernel was never slow. XR-04's 3.1-4.4 ms at best and 10-12 ms median were the time of a submit and a wait on a
device that idles between frames and is shared with other processes, not the time of the dispatch.

- [V] The dispatch alone, by device timestamps around it: **0.09-0.10 ms** for 103 756 rays at 480 x 270 guide
  pixels, within research 16 §5's 0.1-1 ms. Target of this package (1 ms or less): met with a factor of 10.
- [V] The first version of the kernel (XR-04's ray flags) measures the same 0.09-0.10 ms the same way. No change to
  the kernel was needed to reach the target.
- [V] In the same submit the checks now print both: the dispatch 0.091 ms at best and 0.102 ms median by timestamps,
  its submit to idle 0.46 ms and 0.64 ms by the clock of the process. On another run of the same binary: the
  dispatch 2.30 ms at best and 2.38 ms median, its submit to idle 3.2 ms and 3.6 ms; on a third 2.31 ms and 23 ms.
- [V] The slow values are not ray cost: the variant that leaves after the guide (no lamps, no reach test, no ray)
  shows them too (0.04-0.05 ms in a quiet run, 0.5-1.0 ms median in a disturbed one).
- [I] Two causes. The device's clock: the sampled graphics clock was 210 MHz for most of a bench run and 1560-1965 MHz
  at its peaks, and the dispatch time comes in steps (0.09, 0.25-0.45, 0.9, 2.3 ms) that stay level for a whole run
  of frames, as a clock step does. Sharing: submit to idle reaches 20-190 ms at the 90th percentile while the
  timestamps of the same frames stay under 4 ms; another test of this project and a browser held the device.
  Neither applies inside the game's frame, where the device is busy and at full clock.

## How it was measured

`tools/gi_server_test/run.ps1 -Pixel -TestArgs --bench,256`. No checks; per variant of the kernel three runs:

| Run | What |
|---|---|
| One submit | 256 one-sample frames in one command buffer, a timestamp before and after each dispatch. Wall time of the submit / 256 printed beside it as a check of the timestamps |
| A submit a frame | The same, a submit and a wait a frame; timestamps and submit to idle |
| 16 ms idle before each | 64 frames, the process sleeps 16 ms before each submit (an idle device) |

The first eighth of each run is left out; least, median and 90th percentile are printed; all variants run three
times in turn, so a disturbed run shows as a row that differs. Uploads, the copy back and the stats reset are outside
the timestamps. Device load and clock were sampled four times a second beside the bench.

Variants are builds of the one shader (`TRACE`, `STOP`, `LEAN`, `GROUP` in `pixel_shadow.comp`), so before and after
run in the same process on the same acceleration structures.

Not used: a frame profiler of the device's vendor (none installed; timestamps answered the question).

## Results

Least of the three rounds, ms of the dispatch by timestamps, a submit a frame (the steadiest column). Quiet rows of
the other columns agree within 0.02 ms.

Cost by part, kernel as of the first row of the next table:

| Variant | ms | Part |
|---|---|---|
| Guide only | 0.041 | 16 depth reads, position, normal, 64 bytes out: 129 600 pixels |
| + lamps | 0.062 | 7 lamps, the 4 strongest |
| + reach test | 0.062 | 4 lamps x 2 caster bounds: not measurable |
| + rays (the kernel) | 0.087 | 103 756 rays on 21.7 % of the pixels: 0.025 ms |
| Kernel, 16 bytes out, no counters | 0.080 | The 64-byte debug output and two atomic adds: 0.007 ms |
| Kernel, groups of 16 x 16 | 0.107 | Slower than 8 x 8: kept at 8 x 8 |

Before and after each change:

| Step | First version's trace | Kernel |
|---|---|---|
| XR-04 as it was (every candidate to the shader) | 0.087 | - |
| Triangles opaque, first hit ends the ray | 0.087 | 0.087 |
| + class 3 pixels trace one fixed point (XR-05) | 0.088 | 0.088 |
| + numerator and denominator sums out, 96 bytes a pixel (XR-05) | 0.103 | 0.096 |
| + moved caster in reach bit (XR-05) | 0.101 | 0.100 |

Submit to idle of one frame's submit, the number XR-04 printed: 0.18-0.23 ms at best in every quiet run of the
bench; 0.4-3.4 ms at best after 16 ms of idle.

## The candidates of the package, one by one

| Candidate | Finding |
|---|---|
| Acceleration structures rebuilt a frame | [V] No. Four bottom levels and the top level are built once, before the first dispatch, outside every time |
| Ray flags | [V] The first version asked for every candidate (`NoOpaque`), so each triangle on a ray came back to the shader. Changed: triangle geometry is opaque, the ray carries `Opaque`, `TerminateOnFirstHit` and back-face culling; the shader sees capsule boxes only. A ray a delta caster ends asks the static occluders again (a second query, few rays). Same counts on every pixel (the checks against the CPU reference pass unchanged). Gain in this scene: none to 0.007 ms, 1 376 triangles are too few. [I] It matters with a real lot's triangle count |
| A variant with static in the traversal and delta triangles to the shader | [V] Measured equal to both others in the first bench, then removed |
| Divergence, occupancy, group size | [V] 21.7 % of the pixels trace, in groups of 8 x 8: the rays cost 0.025 ms. 16 x 16 is slower by 0.02 ms |
| Loop over 4 lamps and samples | [V] One sample a lamp and frame; part of the 0.025 ms |
| Reach test | [V] Not measurable with 2 casters. [O] It is a loop over all caster bounds per lamp: with tens of casters research 16 §5's tile list is still to build |
| Inner-shell winding (`TRIANGLE_FRONT_COUNTERCLOCKWISE`) | [V] Kept; with opaque geometry the culling stays in the traversal. Self-shadow check unchanged: 16 of 107 485, 1 of 9 643, 0 of 1 457, 1 of 629 |

## Kernel changes for XR-05

| Change | Detail | Check |
|---|---|---|
| Class 3 pixel traces one fixed point | Binding 7: the motion class a full-resolution pixel (a buffer in the harness; the Sim is class 3). Such a pixel takes point (hash of the pixel) mod 16 in every frame; the 16-sample dispatch is unchanged | [V] 1 005 class 3 pixels, all traced: 16 frames are 16 times the first on each. Every other pixel: 16 frames equal the 16-sample dispatch, as before |
| Numerator and denominator out | `num` = sum over the lamps of colour x geometry x d, `den` = the same with u, without A and without the division by the sample count. Over n one-sample frames `m = 1 - sum(num) / (A n + sum(den))` | [V] 16 frames' sums give the 16-sample multiplier within 0.000/255 on every pixel outside class 3. The mean of the 16 frames' multipliers is off by up to 6.3/255: the reason for the second target |
| Moved caster in reach | A caster's bounds carry "moved this frame" in `lo.w`; the caller makes the bounds hold the old and the new place. Out in `num.a` | [V] 14 360 of the 28 105 pixels that traced (the Sim is marked, the chair is not); equal to the reach test done on the CPU from the kernel's guide on 99.9 % or more of the drawn pixels |

## Open issues

- [O] Measured on the harness's lot (1 376 triangles, 6 capsules, 7 lamps, 2 casters). Triangle count, caster count
  and the filter passes of XR-05 are not in the number. XR-06 measures in the bridge pass with these timestamps.
- [O] The clock as the cause of the steps is inferred from the sampled clock and the shape of the times; the clock
  was not pinned to prove it.
- [O] The "one submit" column's least value is not usable (0.003-0.05 ms: timestamps of back-to-back dispatches); its
  median and the wall time over the frame count are.
- [O] `num.a` and the class buffer are harness shapes; XR-06 picks the targets' formats.
- XR-04's note "Time: ... Not analysed" is answered here; its file is not edited.
