## Findings

- Verified: the server only plays Direct3D 9 calls on stock DXVK 3.1.1 (`server.useVanillaDxvk = True`), on one play
  thread with unlocked handle maps. All Direct3D 9 work of GI, including the write of results, belongs on that thread.
- Verified: a client texture crosses the bridge as the client object's id (`client/base.h`), not its pointer; the
  export resolves the pointer to the id, as the asynchronous read-back patch does.
- Verified: DXVK 3.1.1 enables no ray-tracing extension, so rays need a second Vulkan device. DXVK's interop interface
  gives the physical device to match and remains a later zero-copy path for `serverCompute`.
- Verified: DXVK shares textures only as DEFAULT-pool KMT handles and the bridge's `CreateTexture` passes no handle;
  the spec chooses a host copy plus `UpdateSurface` on the play thread under a per-pass byte budget.
- Inferred: TS3 does not create a multithreaded device; two devices coexist with sliced dispatches; the upload stays
  under 1 ms a pass. All three are measured in R-03.
- Coordination: the GI patch follows patch 0015 (asynchronous read-backs), reuses its poll points, `AsyncResult` flag
  and ticket contract, and touches the same switch cases; 0015 should land first.
